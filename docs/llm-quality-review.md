## 의미 검토에서 확인한 문제와 수정

- 목적이 없는 “보증금만 보내주시면 처리됩니다”를 선입금 사기로 과하게 해석했다. 대출·보상·수익·출금 등 의심되는 선납의 대상이 확인되지 않으면 판단 곤란으로 두고 거래 목적을 질문하도록 명시했다.
- 프롬프트 공격 사례의 요약에서 확인되지 않은 “상담원 사칭”을 사실처럼 표현했다. 외부 앱 사례에도 원문에 없는 “강력하게”가 붙었다. 신원·의도·악성 여부를 단정하지 않고 관찰 가능한 요구만 설명하도록 명시했다.
- 인용 일치만으로 해석의 정확성을 증명할 수 없다는 점을 실제 사례에서 확인했다. 서버의 인용·ID 검증을 통과한 응답도 위 두 의미 문제를 포함할 수 있다.

최초 프롬프트 SHA256: `387093e3bc54b5ec99c2575a5ac1a98030bba4cf2759490e10e6754a3d9ae29b`. 최초 결과는 `artifacts/llm-regression.json`에 보존한다. 수정 후 표본 결과를 최초 14건 성적으로 합산하지 않는다.

## 수정 후 재검사

대출·인증번호·외부 앱·예방·정상 정산·공식 앱·프롬프트 공격·맥락 부족의 8건을 같은 모델로 다시 실행했다. 상태 8/8건과 기대 태그가 모두 일치했고 API 오류·재시도는 없었다. 약 1.6초 p50 / 2.9초 p95였다. 보증금 사례는 `needs_context`, 빈 신호·유형 목록과 거래 목적 질문으로 바뀌었다. 최초에 실행 오류가 난 인증번호·공식 앱 사례도 각각 의심·신호 없음으로 정상 응답했다.

이 단계에서도 공격 사례 설명에는 확인되지 않은 “상담원 사칭”이 남아 있었다. 상태 분류 8/8을 설명 품질 전체 통과로 간주하지 않았다. 첫 수정 프롬프트 SHA256은 `90618882611c348fbcef6907e56395dc82103d2011fd40301a384064612327c4`, 결과는 `artifacts/llm-regression-selected-state-fix.json`에 보존했다.

발신자 진위가 미확인이라는 제약을 모든 설명 필드에 명시하고, 실제 원문 인용 외에는 사칭 단정을 하지 않도록 한 번 더 수정했다. 공격 사례 1건을 별도로 재검사해 `suspicious_signals` / `CREDENTIAL_REQUEST`를 유지하면서 “은행 비밀번호와 OTP를 전달하도록 요구함”이라는 관찰 중심 요약과 원문 인용을 확인했다. 마지막 프롬프트 SHA256은 `e750187656ce2f9f29a47a32b078792ae2222e8c5441c4855ce8317447b55c52`, 결과는 `artifacts/llm-regression-selected-explanation-fix.json`에 보존했다.

최종 프롬프트로 14건 전체를 다시 평가한 것은 아니다. 마지막 표현 수정의 재검사는 공격 사례 1건에 한정되며, 다른 입력에서도 의미 오류가 사라졌다고 보장하지 않는다. 전체 개발·보류 비교는 별도 최종 평가로 진행한다.

## 범위와 한계

단일 작성자의 작은 합성 자료이며 독립 라벨 검토나 실사용 성능 시험이 아니다. 수정에 사용한 사례의 재검사는 회귀 확인이며 새로운 블라인드 평가가 아니다. 후속 공식 자료·화면 검증은 [출처 검토](source-review.md)와 [브라우저 점검](browser-review.md)에 별도로 기록했다. 전체 개발·보류 비교는 남아 있다. 모델 혼잡과 타임아웃은 시연 중에도 발생할 수 있다.
